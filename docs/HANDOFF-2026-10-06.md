## 2. 배포 흐름 (반드시 이 순서)

1. 작업 가지에 커밋. 커밋은 `git -c user.name="yonghyeonjee" -c user.email="yonghyeonjee@gmail.com" commit …`
2. `git push -u origin claude/web-folder-v8-replacement-wsm3nu`
3. GitHub 에 PR 열기 → `ci` 워크플로(타입 검사, 빌드, OG 검사 `web/scripts/check-og.mjs`) 통과 확인. 실행 목록은 `name=='ci'` 와 head_sha 로 거른다
4. squash 머지
5. `git fetch origin main && git checkout -B claude/web-folder-v8-replacement-wsm3nu origin/main && git push --force-with-lease`
6. `deploy_aws.yml` 이 main 푸시로 돈다(빌드는 Actions 에서, 서버는 받기만). 끝나면 서버에서 `curl 127.0.0.1:3000` 이 200 인지 본다
7. 운영 확인: `probe.yml` 을 `script=probe_src.py`, `arg=주소1,주소2` 로 수동 실행 → 잡 로그에서 status·title·링크 수 확인. 브라우저가 필요하면 `probe_browser.py`(검사 항목 map, mini:, srch:, org:). 서울 IP 에서만 열리는 곳은 `server_probe.yml`(서버의 `/api/cron/probe?url=…&snip=…`)
8. 주의: 서버를 부르는 수집(org_sites 의 서버 단계)이 도는 중에 배포하면 서버 재시작으로 그 수집이 끊긴다. 러너에서 도는 것(cron_jobs, weekly_sources, qnet_site, alio, collect_manual)은 배포와 무관하다. 수집 코드를 러너에서 돌리는 틀은 `web/scripts/cron.ts` 와 `.github/actions/runner-cron`; 비밀값은 GitHub Secrets 를 env 로 넘긴다

### Vercel 에선 왜 없던 일인가

Vercel 은 요청마다 함수 하나를 띄우고 끝나면 거둬 간다. 메모리가 쌓일 틈이 없고, 모자라면 기계를 더 붙인다. Lightsail 은 1GB 기계 한 대에서 Node 프로세스 하나가 며칠이고 돈다. 캐시·힙이 시간이 갈수록 자라고, OS·Caddy 와 같은 1GB 를 나눠 쓴다. 그래서 세 번의 장애가 모두 "프로세스 메모리 상한이 기계에 안 맞음" 한 종류였다. 유입(하루 100명)이나 CPU(5% 안팎, 버스트 잔량 65%) 와는 무관. 상한을 기계보다 넉넉히 작게 두고(힙 384MB < MemoryHigh 640MB < 기계 909MB), 굳으면 지킴이가 1~2분 안에 다시 띄우는 것으로 막는다. 다음 단계가 필요하면 기계를 2GB 플랜으로 올리는 것이 가장 싼 길이다.

### 원인(세 가지가 겹침)
1. 잡알리오(alio)를 붙이며 공고 조회를 `.in("source", ["gojobs","alio"])` 로 바꿨다. SQL 의 `source = ANY(...)` 는 `(source, reg_date, end_date)` 인덱스의 정렬을 못 써 23만 건을 매번 다 읽고 정렬했다. Nano 가 못 견뎠다.
2. 되돌릴 때 출처를 하나로 줄였지만 `.in()` 은 그대로 둬서 똑같이 인덱스를 못 탔다(0.7초, 느린 디스크면 3초 초과).
3. 화면용 DB 요청에 제한 시간이 없어 DB 가 멈추면 요청이 쌓여 서버가 함께 죽었다.
4. `jiwon.service` 의 메모리 상한(380/450MB)이 기계의 실제 메모리(412MB)보다 커서, Node 가 커지면 cgroup 이 끊지 않고 기계 전체가 스왑으로 밀렸다. 두 번째 502 의 직접 원인.
