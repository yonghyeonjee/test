## 2. 배포 흐름 (반드시 이 순서)

1. 작업 가지에 커밋. 커밋은 `git -c user.name="yonghyeonjee" -c user.email="yonghyeonjee@gmail.com" commit …`
2. `git push -u origin claude/web-folder-v8-replacement-wsm3nu`
3. GitHub 에 PR 열기 → `ci` 워크플로(타입 검사, 빌드, OG 검사 `web/scripts/check-og.mjs`) 통과 확인. 실행 목록은 `name=='ci'` 와 head_sha 로 거른다
4. squash 머지
5. `git fetch origin main && git checkout -B claude/web-folder-v8-replacement-wsm3nu origin/main && git push --force-with-lease`
6. `deploy_aws.yml` 이 main 푸시로 돈다(빌드는 Actions 에서, 서버는 받기만). 끝나면 서버에서 `curl 127.0.0.1:3000` 이 200 인지 본다
7. 운영 확인: `probe.yml` 을 `script=probe_src.py`, `arg=주소1,주소2` 로 수동 실행 → 잡 로그에서 status·title·링크 수 확인. 브라우저가 필요하면 `probe_browser.py`(검사 항목 map, mini:, srch:, org:). 서울 IP 에서만 열리는 곳은 `server_probe.yml`(서버의 `/api/cron/probe?url=…&snip=…`)
8. 주의: 서버를 부르는 수집(org_sites 의 서버 단계)이 도는 중에 배포하면 서버 재시작으로 그 수집이 끊긴다. 러너에서 도는 것(cron_jobs, weekly_sources, qnet_site, alio, collect_manual)은 배포와 무관하다. 수집 코드를 러너에서 돌리는 틀은 `web/scripts/cron.ts` 와 `.github/actions/runner-cron`; 비밀값은 GitHub Secrets 를 env 로 넘긴다

### Vercel 에선 왜 없던 일인가

Vercel 은 요청마다 함수 하나를 띄우고 끝나면 거둬 간다. 메모리가 쌓일 틈이 없고, 모자라면 기계를 더 붙인다. Lightsail 은 1GB 기계 한 대에서 Node 프로세스 하나가 며칠이고 돈다. 캐시·힙이 시간이 갈수록 자라고, OS·Caddy 와 같은 1GB 를 나눠 쓴다. 그래서 세 번의 장애가 모두 "프로세스 메모리 상한이 기계에 안 맞음" 한 종류였다. 유입(하루 100명)이나 CPU(5% 안팎, 버스트 잔량 65%) 와는 무관. 상한을 기계보다 넉넉히 작게 두고(힙 384MB < MemoryHigh 640MB < 기계 909MB), 굳으면 지킴이가 1~2분 안에 다시 띄우는 것으로 막는다. 다음 단계가 필요하면 기계를 2GB 플랜으로 올리는 것이 가장 싼 길이다.

### 원인(세 가지가 겹침)
1. 잡알리오(alio)를 붙이며 공고 조회를 `.in("source", ["gojobs","alio"])` 로 바꿨다. SQL 의 `source = ANY(...)` 는 `(source, reg_date, end_date)` 인덱스의 정렬을 못 써 23만 건을 매번 다 읽고 정렬했다. Nano 가 못 견뎠다.
2. 되돌릴 때 출처를 하나로 줄였지만 `.in()` 은 그대로 둬서 똑같이 인덱스를 못 탔다(0.7초, 느린 디스크면 3초 초과).
3. 화면용 DB 요청에 제한 시간이 없어 DB 가 멈추면 요청이 쌓여 서버가 함께 죽었다.
4. `jiwon.service` 의 메모리 상한(380/450MB)이 기계의 실제 메모리(412MB)보다 커서, Node 가 커지면 cgroup 이 끊지 않고 기계 전체가 스왑으로 밀렸다. 두 번째 502 의 직접 원인.

## 10. 봇 막기 — 2026-10-14

- **접속 기록**: Caddy 가 `/var/log/caddy/access.log` 에 요청마다 한 줄(JSON). IP·시각·주소·이름표·리퍼러·언어만, 20MB×7, 7일 뒤 삭제. 개인정보 처리방침에 적었다.

- **유입 통계**: 언어 머리글이 없는 요청과 언어 목록이 빈 브라우저는 세지 않는다(10-10 부터 시간당 40건쯤 끼던 수집기).

  처음 그리는 쪽은 캐시 안 되는 500, 재생성 실패면 옛 정상 쪽이 그대로 나간다. 이야기 쪽은 getStoryStrict, 채용 쪽의 기관 이야기 곁가지는 느슨한 getStory.
- **새 쿼리를 쓸 때**: try/catch 로는 DB 오류를 못 잡는다. 상세 쪽 로더는 반드시 error 를 직접 본다.
- **캐시 점검**: Actions → server-diag 가 '내려간 공고'로 굳은 채용 쪽 수와 404 메타로 굳은 사업 쪽 수를 센다(10-16: 0/280, 1/209).
  ssh 따옴표 안이라 안쪽 따옴표는 큰따옴표만 쓴다.
- **남은 일**(승인 뒤): getRelated 순환, 지역·주제 허브 페이지 나눔, jobText 고정 문단 정리, 기업지원 경로형 허브, 사업 사이트맵 확대,

## 20. 잡알리오를 채용 목록·사이트맵에 다시 넣음(2026-10-17)

- `JOB_SOURCES = ["gojobs", "alio"]`. 10-06 장애 뒤 생긴 두 출처용 부분 색인(job_posts_pub_reg_idx) 덕에 목록·사이트맵·검색·지도는
  쿼리마다 EXPLAIN 으로 재어 0.5~7ms 로 같다. 기관(org) 조회만 (org, reg_date) 색인이 나라일터 부분 색인이라
  `perSource` 로 출처마다 따로 읽어 합친다(관련 공고·기관 쪽). DB 가 378MB 라(무료 한도 500MB) 새 색인은 만들지 않았다.
- **쌍둥이 공고**: 같은 공고가 두 곳에 다 있으면 lib/jobTwins `dropAlioTwins` 가 잡알리오 쪽을 뺀다(등록일·마감일이 같고
  제목이 같거나 한쪽이 품음). 목록·지역·기관·관련·사이트맵·지도·검색·브리핑 글(blog_daily `drop_alio_twins`)에 다 건다.
  접수 중 잡알리오 305건 중 25건이 쌍둥이였고, 검토에서 25건 모두 진짜 같은 공고였다. 관련 공고는 지금 보는 공고의 쌍둥이도 뺀다.
- **목록 창**: 최근 1,000건 + 접수 중 전부. **PostgREST 는 요청 한 번에 1,000줄까지만 준다**(.limit(3000) 이어도 1,000). 1,000줄을
  넘을 수 있는 읽기는 `readAll` 로 나눠 읽는다(목록의 접수 중, 지역 목차, 사이트맵, 지도). 지역 쪽도 최근 200건 + 접수 중 전부.
- **사이트맵**: 접수 중 전부(최대 1,500, 1년 안 등록), 모자라면 최근 마감으로 400건까지. 같은 날은 번호순이라 빌드마다 같다.
- **지역 목차**(getJobRegions): 순서 없이 5,000줄을 세서 강원·경기 둘만 나오던 것을 고정 시·도 목록 + 접수 중 건수로.
  건수는 지역 쪽과 같은 기준(region 이 그 시·도이거나 기관명·제목에 그 이름).
  지역 쪽은 시·도가 아닌 이름이면 404, 건수(count) 조회는 뺐다(두 글자 ILIKE 로 평균 1.2초 걸리던 것).
- **숫자**: job_overview·job_org_stats 등 집계(matview)는 나라일터만 그대로 둔다(잡알리오는 2026-08 부터라 섞으면 추이가 틀어짐).
  채용 첫 화면은 잡알리오 수를 더하고(getAlioCounts), 기관 쪽 머리 숫자는 목록에서 센다. 통계 카드는 "나라일터 공고 기준".
- 잡알리오 지역 "해외"는 region 을 비운다(수집 때 normSido 만, 기존 5건은 UPDATE 로 비움, 원문은 raw.area).
- 목록 카드: 잡알리오 배지, 잡알리오는 접수 시작일이 없어 "마감"만, 채용 구분의 "외 N"은 "등".
