## 1. 한눈에

**결론: 순위가 떨어진 것이 아닙니다. 페이지가 색인에서 빠지고 있을 가능성이 가장 큽니다.** 평균 게재순위는 7~9위 그대로인데 노출만 450에서 3으로 줄었습니다. DB가 느려지는 순간 멀쩡한 채용 공고가 "내려간 채용 공고"라는 noindex 페이지로 만들어집니다. 그 페이지는 3일 동안 캐시됩니다. 구글은 이것을 정상 200 응답으로 받고 색인에서 지웁니다. 서버 로그에는 200만 남기 때문에 지금까지 드러나지 않았습니다.

| 날짜 | 10-08 | 10-09 | 10-10 | 10-11 | 10-12 | 10-13 | 10-14 |
|---|---|---|---|---|---|---|---|
| 노출 | 262 | 349 | 450 | 115 | 61 | 11 | 3 |
| 클릭 | 13 | 9 | 7 | 0 | 0 | 0 | 0 |

가장 큰 원인 세 가지는 다음과 같습니다.

1. **DB 오류가 '내려간 공고'로 둔갑합니다.** 공고를 읽는 함수가 DB 오류를 "공고 없음"으로 받아들입니다. 채용 페이지는 200과 noindex로 나가고, 지원사업 페이지는 404로 나갑니다. 둘 다 3일 캐시됩니다. 구글봇 요청의 80%가 채용 페이지입니다. 코드 결함은 확실합니다. 이것이 폭락의 원인이라는 판단은 가능성이 높지만 아직 증명되지 않았습니다.
2. **약한 DB, 크롤 폭주, 잦은 배포가 이 결함을 키웁니다.** Supabase Nano는 한도를 넘은 상태입니다. 홈 화면 조회 하나만 해도 하루 약 83번 시간 초과가 납니다. 10월 8~9일과 13~14일 폭주 때는 부하가 더 컸습니다. 배포할 때마다 캐시가 비기 때문에 봇이 약한 DB를 상대로 페이지를 새로 그립니다. 하루 8~12번 배포한 날도 있었습니다.
3. **회복을 늦추는 콘텐츠 약점이 있습니다.** 요약이 없는 채용 페이지는 문단 대부분이 모든 페이지에서 똑같습니다. 지원사업 약 7,600개 중 대부분은 색인되는 페이지로부터 받는 링크가 없습니다. 둘 다 폭락을 일으킨 원인은 아닙니다. 회복할 수 있는 높이를 정하는 요인입니다.

**시점도 맞습니다.** 폭락은 10월 11일에 시작해 13~14일 폭주보다 먼저 왔습니다. 8~9일 장애 때와 평소 시간 초과 때 noindex 페이지가 생겼고, 구글이 그 페이지를 다시 크롤하면서 색인에서 뺐다고 보면 시점이 들어맞습니다.

**회복을 막는 것은 1번입니다.** 이 결함이 남아 있으면 DB가 흔들릴 때마다 새 noindex 페이지가 생깁니다. 고칠 곳은 함수 두세 개, 몇 줄입니다. 배포하면 새 릴리스 폴더가 빈 캐시로 시작합니다. 그래서 이미 오염된 페이지도 같이 사라집니다.

**의뢰 내용 하나를 바로잡습니다.** 의뢰서에는 "DB 시간 초과 때 채용 페이지 로더가 예외를 던져 5xx가 난다"고 되어 있습니다. 실제 코드는 그렇게 동작하지 않습니다. 예외 없이 200과 noindex를 돌려줍니다.

**오늘 바로 확인할 수 있습니다.** 서치 콘솔 페이지 색인 생성 보고서에서 "'noindex' 태그에 의해 제외됨"이 10월 9일 무렵부터 늘었는지 보세요. 예시에 /jobs/ 주소가 있는지도 보세요. 예전에 순위가 있던 채용 주소를 URL 검사로 열었을 때 크롤된 페이지 제목이 "내려간 채용 공고"로 나오면 원인은 거의 확실합니다.

## 2. 확인된 문제와 할 일

### 확인된 문제

**높음**

- **DB 오류를 '없는 공고'로 읽고, 그 결과를 캐시합니다.** 결함은 확실합니다. 폭락 원인일 가능성은 높습니다.
  - 무엇: getJob 함수는 DB 오류가 나면 예외가 날 것이라 보고 try/catch를 두었습니다. 그런데 지금 쓰는 postgrest-js 2.115.0은 예외를 던지지 않습니다. 12초 시간 초과든 PostgREST 오류든 `{ data: null, error }` 값으로 돌려줍니다. 그래서 catch는 실행되지 않고 "없음" 쪽으로 흘러갑니다. 지원사업 함수 getProgram과 이야기 함수 getStory도 구조가 같습니다.
  - 근거:

    | 위치 | 코드 | 결과 |
    |---|---|---|
    | web/lib/pubJobs.ts:254-260 | `error`를 읽지 않고 `if (!data) return null` | DB 오류가 "없음"으로 처리됨 |
    | web/node_modules/@supabase/postgrest-js/dist/index.mjs:416-455 | fetch 실패와 abort를 error 값으로 반환 | catch가 실행되지 않음 |
    | web/lib/db.ts:34-38 | 12초 `AbortSignal.timeout` | 시간 초과도 error 값으로 반환 |
    | web/app/jobs/[id]/page.tsx:82-86 | 제목 "내려간 채용 공고", `index: false` | 200과 noindex |
    | web/app/jobs/[id]/page.tsx:195-200 | `<JobGone />` 렌더 | 본문이 다른 공고 목록으로 바뀜 |
    | web/app/jobs/[id]/page.tsx:38 | `revalidate = 259200` | 3일 캐시 |
    | web/lib/db.ts:245-252 | getProgram도 `error` 무시 | 지원사업 페이지가 404 |
    | web/app/p/[id]/page.tsx:39, 106-107 | `revalidate = 259200`, `notFound()` | 404를 3일 캐시 |

  - 영향:
    - 채용 페이지는 구글봇 요청 398건 중 317건을 차지하고, 노출도 대부분 여기서 나옵니다.
    - 첫 렌더나 백그라운드 재생성이 DB가 느린 순간에 걸리면 정상 페이지 자리를 noindex 페이지가 3일 동안 차지합니다.
    - 로그에서 398건 중 396건이 200이었던 이유도 여기 있습니다. 실패가 200 응답 안에 숨어 있습니다.
    - 구글은 noindex와 404를 일시 오류로 보지 않습니다. 삭제 신호로 받아들입니다.
  - 고치는 법:
    1. getJob을 이렇게 바꿉니다. `const { data, error } = await db.from("job_posts")...eq("source_id", sourceId).limit(1).maybeSingle(); if (error) throw new Error(...); if (!data) return null;` `.limit(1)`을 붙이면 같은 공고 행이 둘 있어도 오류가 나지 않습니다. job_posts의 유일 키 정의는 sql 폴더에 없어서 확인하지 못했습니다.
    2. getProgram에도 `if (error) throw` 한 줄을 넣습니다.
    3. getStory는 이야기 페이지에서만 쓰는 엄격한 버전을 따로 만듭니다. 채용 페이지 page.tsx:209의 기관 이야기 호출은 실패해도 null을 받게 둡니다. 부가 정보 하나 때문에 채용 페이지 전체가 500이 되면 안 됩니다.
    4. 손대지 않을 것: findJobSource와 JobGone 안의 `.catch`, 목록 로더, error.tsx 추가, notFound 전환은 그대로 둡니다. JobGone.tsx:13-18에는 이 구역에서 notFound가 200으로 나갔던 기록이 있습니다. 캐시를 릴리스 폴더 밖으로 옮기는 것도 하지 않습니다. 옛 빌드의 HTML이 섞이고, 10월 9일 같은 디스크 문제가 다시 생깁니다.
    5. 고친 뒤 동작: 처음 그리는 페이지가 DB 오류를 만나면 500이 나가고, 이 500은 캐시되지 않습니다. 재생성이 실패하면 이전의 정상 페이지가 계속 나갑니다. 구글은 짧은 5xx를 일시 오류로 봅니다. 대신 폭주 때는 캐시가 없는 요청마다 DB를 다시 부르게 됩니다. 이 부분은 지금 있는 Caddy와 fail2ban 제한이 막아 줍니다.
    6. 선택: Caddy에서 페이지 경로의 upstream 5xx를 503과 Retry-After로 바꿔 내보냅니다. 구글봇, bingbot, Yeti, Daum 예외는 그대로 둡니다.

    1. 주제 배지를 `/topic/{slug}` 링크로 감쌉니다.
    2. getRelated는 확신도순 대신 source_id 다음 순서로 가져옵니다. 5개가 모자라면 처음부터 채웁니다. 쿼리는 하나로 유지합니다. 이렇게 하면 모든 사업이 적어도 한 곳에서 링크를 받습니다.

## 3. 괜찮은 것과 지켜볼 지표

### 괜찮은 것

- **robots.txt 차단 알림은 정상입니다.** 막힌 주소는 /saved, /search?q=, /jobs/*/q/처럼 원래 noindex였던 곳입니다. 차단을 풀면 10월 9일 같은 디스크 문제가 다시 생깁니다.
- **봇 차단 규칙은 구글을 막지 않습니다.** Caddy는 색인 대상 경로에서 구글봇에 403을 내지 않습니다. fail2ban은 구글봇, bingbot, Yeti, Daum, Applebot을 예외로 둡니다. 10월 14일 이후 flood 차단은 0건입니다.
- **robots.txt가 사이트 전체를 막을 위험은 낮습니다.** DB가 실패하면 색인 허용 기본값으로 돌아갑니다. 구글봇이 하루 100건 넘게 페이지를 가져간 것도 그 증거입니다.
- **사이트맵 구성은 맞습니다.** 차단, noindex, 리다이렉트 주소가 없고, 전체 주소는 2~3천 개입니다. 분할 전후 주소 목록도 같습니다.
- **기본 메타 정보가 갖춰져 있습니다.** canonical, metadataBase, html lang ko, og 태그, 페이지당 h1 하나가 맞게 들어 있습니다. 네이버 확인 태그와 Daum 소유 확인 줄도 있습니다.
- **구조화 데이터 형식은 맞습니다.** 탐색경로와 JobPosting 기본 필드가 정상입니다. 마감 공고에 지난 validThrough를 남겨 두는 것은 구글이 허용하는 방식입니다.
- **사이트명 변경과 사이트맵 분할은 주원인일 가능성이 낮습니다.**
- **제목 중복, 긴 제목, 틀에 맞춘 JobPosting 설명은 폭락 원인이 아닙니다.** 노출이 늘던 10월 2일부터 10일까지도 똑같았습니다. 나중에 다듬으면 됩니다.
- **목록 필터와 페이지 나눔은 범위가 정해져 있습니다.** 크롤을 낭비한다는 증거가 없습니다. noindex를 붙여도 크롤은 줄지 않습니다.
- **10월 10~12일 서버 멈춤은 주원인이 아닙니다.** 한 번에 1~3분이라 구글봇이 실패를 만날 확률이 낮습니다. 운영 안정성 측면에서는 따로 볼 가치가 있습니다.
- **배포 재시작은 거의 무중단입니다.** 10월 11일과 12일에는 배포가 없었습니다.
- **og 이미지의 한글은 자동 글꼴로 제대로 나옵니다.** og 이미지는 순위 신호도 아닙니다.
- **IndexNow 설정은 맞습니다.** Google Indexing API는 비밀값이 없어 한 번도 돌지 않았습니다. 그래서 하락과 관계가 없습니다.
